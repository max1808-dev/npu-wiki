This page documents the operators supported by the Ethos-U Neural Processing Units (NPUs) when using the Vela compiler. It details which TensorFlow Lite and TOSA operators can be executed on the NPU hardware, along with their constraints and requirements. For information about how operators are optimized during compilation, see Graph Optimization.

Overview of Operator Support System

The Vela compiler determines whether operators in a neural network model can run on Ethos-U NPUs or need to be executed on the CPU. This decision is based on a series of checks:

  1. Is the operation type supported by the NPU architecture?
  2. Does the operation meet the generic constraints that apply to most operators?
  3. Does the operation meet specific constraints for its particular type?

If any of these checks fail, the operation will be scheduled to run on the CPU instead of the NPU.

Constraints Categories

Operator constraints are classified into two categories:

Generic Constraints

These are fundamental requirements that most operators must satisfy to run on the NPU:

  • All required operator attributes must be specified
  • Input and output tensors must not be dynamic
  • Tensors must have defined shapes (no None dimensions)
  • Tensor dimensions must be in the range [1, 65535]
  • Most operators require batch size of 1
  • Supported data types are int8, uint8, int16, and int32 (with certain operator restrictions)
  • Per-axis quantization is only supported for specific operators
  • If fused activation functions are present, they must be of supported types

Specific Constraints

These are requirements unique to each operator type. Examples include:

  • Convolution kernel size limits
  • Filter dimension constraints
  • Stride and dilation restrictions
  • Padding requirements
  • Shape compatibility between inputs and outputs

Architecture-Specific Operator Support


The Ethos-U product line includes different NPU architectures, each with slight variations in operator support:


Ethos-U55 and Ethos-U65


These architectures support a common set of operators with identical constraints. Key supported operators include:


    

  • Conv2D, DepthwiseConv2D, TransposeConv
    • 

  • MaxPool2D, AveragePool2D
    • 

  • Add, Mul, Sub, Maximum, Minimum
    • 

  • Relu, Relu6, Tanh, Sigmoid, LeakyRelu
    • 

  • Reshape, Squeeze, Transpose
    • 

  • FullyConnected (with restrictions)
    • 

  • LSTM (with restrictions)
    • 

  • And many more
    • 



Ethos-U85


The Ethos-U85 architecture supports most of the operators supported by U55/U65 plus additional ones:


    

  • BatchMatMul
    • 

  • Gather
    • 

  • Scatter
    • 



Additionally, some constraints may differ between architectures. For example, stride limits, filter dimensions, and other hardware-specific capabilities can vary.

Detailed Constraints Examples


Let's examine some specific operator constraints in detail:


Convolution (Conv2D) Constraints


Conv2D operators have several specific constraints:


    

  • Stride values must be within certain limits:

      

    • Stride height must be between 1 and 3 when output height > 1
      • 

    • Similar constraints for stride width
      • 

    

    • 

  • Dilated kernel height must be between 1 and 64
    • 

  • Product of dilated kernel width and height must be between 1 and 4096
    • 

  • Weight tensor must be 8-bit and constant
    • 

  • Optional bias tensor must be 1D and of type int32 or int64
    • 

  • Bias tensor values must fit within 40 bits
    • 



Pooling Constraints


For pooling operations like MaxPool2D and AvgPool2D:


    

  • Kernel filter dimensions have maximum sizes (typically 8x8 for AvgPool with SAME padding)
    • 

  • AvgPool with VALID padding can support larger filter dimensions
    • 

  • MaxPool supports larger filter dimensions regardless of padding
    • 



Element-wise Operator Constraints


Operators like Add, Mul, Sub have their own requirements:


    

  • At least one input shape must match the output shape

  • Both input data types must match
    • 

  • For signed input data types, output must also be signed
    • 

  • Broadcasting is only allowed for rank indices with dimension 1

Using the Supported Operators Report


To see the complete list of supported operators for your target device, you can use the --supported-ops-report flag with the Vela compiler. This generates a detailed report of all supported operators and their constraints:


vela --supported-ops-report



The report includes:


    

  • Summary tables for each Ethos-U architecture
    • 

  • Generic constraints applicable to most operators
    • 

  • Detailed operator-specific constraints for each architecture
    • 



This information can help you design your neural network to ensure high NPU utilization by avoiding operations that would force execution on the CPU.


Testing Operator Support


When developing models for Ethos-U NPUs, you can use several approaches to check if your operators will be supported:


    

  1. Use the Vela compiler with the --show-cpu-operations flag to identify operations that will run on the CPU

  2. Review the output log for warnings about unsupported operators
    3. 

  3. Consult the generated supported operators report for detailed constraints
