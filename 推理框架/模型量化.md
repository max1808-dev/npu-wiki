# 模型量化（Quantization）

> 本文以 TensorFlow `Conv2D + BiasAdd + ReLU` 模型为例，解释量化的基本原理、量化的目的、量化在模型部署流程中的位置，以及量化对模型参数、模型文件和运行时内存的影响。
>
> 本文聚焦**量化及其对模型表示和存储的影响**，不展开讨论 Converter 内部实现，也不讨论量化校准算法的具体实现细节。

## 1. 什么是模型量化？

模型量化（Quantization）是将模型中的数值从较高精度的数据表示转换为较低位宽的数据表示的过程。例如：

- FP32 → INT8
- FP32 → FP16
- FP32 → INT16

在嵌入式 NPU 场景中，最常见、最值得重点研究的是 **FP32 → INT8**。

例如，FP32 权重可能是：

```text
0.125
-0.238
0.567
-0.891
0.012
...
```

INT8 只能表示：

```text
-128 ~ 127
```

因此，量化不是简单地把 FP32 文件压缩成 INT8 文件，而是建立浮点数与整数之间的映射关系，使整数能够近似表示原来的实数。

### 1.1 一个直观例子

假设原始权重为 `0.5`，采用对称量化：

\[
S = \frac{1}{127}, \qquad Z = 0
\]

量化公式：

\[
q = round\left(\frac{r}{S}\right)+Z
\]

代入：

\[
q = round(0.5 \times 127) = 64
\]

反量化公式：

\[
r \approx (q-Z)\times S
\]

因此：

\[
r \approx 64/127 \approx 0.50394
\]

| 项目 | 数值 |
|---|---:|
| 原始 FP32 | 0.5 |
| Scale | 1/127 ≈ 0.007874 |
| Zero Point | 0 |
| 量化后 INT8 | 64 |
| 反量化近似值 | 0.50394 |
| 量化误差 | 约 0.00394 |

量化会引入误差。量化方案的目标是在满足目标精度的前提下，尽可能降低数据位宽和计算成本。

### 1.2 Scale 和 Zero Point

常见的仿射量化（Affine Quantization）使用两个参数：

- **Scale（缩放因子）**：决定整数步长，一个整数单位对应多少实数。
- **Zero Point（零点）**：表示实数 0 对应的整数值。

量化公式：

\[
q = clamp\left(round\left(\frac{r}{S}\right)+Z,\ q_{min},q_{max}\right)
\]

反量化公式：

\[
r \approx (q-Z)\times S
\]

其中：

| 符号 | 含义 |
|---|---|
| \(r\) | 原始实数值 |
| \(q\) | 量化后的整数值 |
| \(S\) | Scale |
| \(Z\) | Zero Point |
| \(q_{min}\) | 目标整数类型的最小值 |
| \(q_{max}\) | 目标整数类型的最大值 |
| `clamp` | 将结果限制在目标整数范围内 |

例如 INT8 的整数范围通常为 `[-128, 127]`。实际量化时，具体范围、舍入规则以及是否保留某些整数值，要遵循所采用的量化规范和算子约定。

### 1.3 对称量化与非对称量化

#### 对称量化（Symmetric Quantization）

通常令：

\[
Z=0
\]

于是：

\[
r \approx q\times S
\]

例如：

```text
FP32:  -1.0     0.0     0.5     1.0
INT8:  -127      0       64     127
```

优点：

- 权重的 Zero Point 为 0 时，整数乘法和累加的实现更简单。
- 可以减少部分 Zero Point 修正计算。
- 适合 NPU 的整数 MAC 数据通路。

#### 非对称量化（Asymmetric Quantization）

Zero Point 可以不为 0。例如：

\[
S=0.02,\qquad Z=-3
\]

此时实数 0 映射为整数 -3，而不是整数 0。

非对称量化可以更灵活地利用整数表示范围，尤其适用于数值分布不以 0 为中心的 Activation。

**注意：**“权重通常对称、Activation 通常可以非对称”是常见的 TFLite INT8 量化约定，不应将其理解为所有模型、所有算子和所有量化格式都必须如此。具体要求应以对应版本的 TFLite 量化规范为准。

### 1.4 Per-Tensor 与 Per-Channel Quantization

这两个概念对 NPU 编译器和硬件设计非常重要。

#### Per-Tensor Quantization

一个 Tensor 的所有元素共用一组量化参数：

```text
Weight:
    shape = [3, 3, 3, 4]
    scale = 0.01
    zero_point = 0
```

#### Per-Channel Quantization

一个 Tensor 的不同通道使用不同的量化参数。

例如 Conv2D 有 4 个输出通道：

```text
Channel 0: scale = 0.010
Channel 1: scale = 0.015
Channel 2: scale = 0.008
Channel 3: scale = 0.020
```

不同输出通道的权重数值范围可能不同。每个通道使用自己的 Scale，可以更好地利用 INT8 表示范围，降低量化误差。

对于常见的 TFLite INT8 Conv2D 规范，权重支持按输出通道量化；量化维度对应权重的输出通道维度。具体张量布局和维度编号应以模型 Schema 与算子规范为准。

## 2. 为什么要量化？

量化的主要收益包括减少模型存储、降低数据搬运量、提高整数计算效率，以及降低系统能耗。

### 2.1 减少模型存储空间

假设模型有 100 万个参数：

| 数据类型 | 单个参数大小 | 100 万个参数的理论存储量 |
|---|---:|---:|
| FP32 | 4 Bytes | 4 MB |
| FP16 | 2 Bytes | 2 MB |
| INT8 | 1 Byte | 1 MB |
| INT4 | 0.5 Byte | 0.5 MB |

INT8 相比 FP32，参数数据本身的存储量理论上减少 75%。

实际模型文件还包含 Tensor 描述、算子参数、量化元数据、对齐填充等内容，所以整个文件大小不一定严格缩小到四分之一。

### 2.2 减少内存带宽需求

假设一次计算需要读取 100 万个权重：

- FP32：约 4 MB。
- INT8：约 1 MB。

在权重数量相同的情况下，INT8 权重数据量是 FP32 的四分之一。

可能带来的收益：

- 减少 SRAM 读取压力。
- 减少 Flash 到 SRAM 的搬运量。
- 减少 DMA 传输数据量。
- 降低片上总线和存储系统的流量。
- 降低数据搬运能耗。

对 NPU 来说，性能瓶颈不一定只在 MAC 计算单元，也可能在 SRAM、DMA 或外部存储带宽。量化能够减少数据量，但最终性能收益仍取决于整个数据通路。

### 2.3 提高计算效率

FP32 卷积：

\[
Y=X_{FP32}\times W_{FP32}
\]

INT8 卷积的主要乘法：

\[
Acc=\sum_i X_{INT8,i}\times W_{INT8,i}
\]

INT8 乘法器和数据通路通常可以比 FP32 浮点数据通路更紧凑。在相同芯片面积和功耗预算下，硬件设计者可以考虑：

- 放置更多 INT8 MAC 单元。
- 提高并行计算能力。
- 缩小部分数据通路。
- 降低计算单元能耗。

但 **INT8 不意味着性能一定提升 4 倍**。实际性能取决于 MAC 阵列规模、时钟频率、存储带宽、数据布局、算子实现和调度效率。

### 2.4 降低系统能耗

量化可能减少：

1. 模型常量数据的存储容量。
2. SRAM 读写的数据量。
3. 总线和 DMA 传输的数据量。
4. 计算单元的数据位宽。

因此，通常有助于降低系统能耗。对于 SRAM、Flash、带宽和功耗预算有限的 MCU + NPU 系统，量化尤其重要。

## 3. 量化在模型开发和部署流程中的位置

量化通常发生在模型训练之后、部署模型生成过程中。它不是 TensorFlow 模型定义时就必须执行的操作。

```text
TensorFlow 模型开发
    |
    v
模型训练
    |
    |  得到 FP32 Weights、Bias
    v
量化（Quantization）
    |
    |  计算/确定 Scale、Zero Point
    |  将权重及相关 Tensor 转换为目标数据类型
    v
TFLite 模型生成
    |
    |  FlatBuffer 中保存 Tensor 描述、算子和常量数据
    v
图编译器（例如 Vela）
    |
    |  分析算子、量化信息、硬件映射和内存规划
    v
NPU Runtime
    |
    v
NPU 执行推理
```

### 3.1 训练后量化（PTQ）

PTQ：Post-Training Quantization。

模型训练完成后再进行量化，不需要重新训练模型。

```text
TensorFlow FP32 Model
        |
        v
     Converter
        |
        v
   Quantization
        |
        v
   TFLite INT8 Model
```

权重可以根据其数值分布确定量化参数。对于输入、输出和中间 Activation，若要生成全整数模型，通常还需要 Representative Dataset（代表性数据集）进行 Calibration（校准），以估计实际推理时的 Activation 数值范围。

代表性数据集应能反映真实应用中的输入分布。样本数量没有对所有模型都适用的固定值，应根据模型、数据分布和精度验证结果确定。

### 3.2 量化感知训练（QAT）

QAT：Quantization-Aware Training。

训练过程中模拟量化误差，使模型参数适应低精度表示。

```text
TensorFlow Model
        |
        v
插入 Fake Quantization
        |
        v
      Training
        |
        v
   Quantized Model
        |
        v
   TFLite INT8 Model
```

Fake Quantization（伪量化）通常是在训练的前向计算中模拟量化和反量化效果，并不意味着训练过程中的所有参数都实际以 INT8 保存。训练通常仍使用浮点数运算。

最终导出时，才生成部署所需的量化模型。

如果 PTQ 造成的精度损失无法接受，可以考虑 QAT。

### 3.3 PTQ 与 QAT 的区别

| 项目 | PTQ | QAT |
|---|---|---|
| 量化发生阶段 | 训练完成后 | 训练过程中模拟量化 |
| 是否需要重新训练 | 通常不需要 | 需要训练或微调 |
| 开发成本 | 通常较低 | 通常较高 |
| 精度适应能力 | 取决于模型和校准数据 | 可通过训练适应量化误差 |
| 最终部署格式 | 可以是 INT8 等量化格式 | 可以是 INT8 等量化格式 |

QAT 是训练方法，不是一个独立的最终文件格式。PTQ 和 QAT 都可以生成符合目标部署规范的量化模型。

## 4. 量化对模型参数和 Tensor 的影响

下面继续使用 `Conv2D + BiasAdd + ReLU` 示例。

### 4.1 原始 TensorFlow 模型

```python
import tensorflow as tf

class ConvRelu(tf.Module):

    def __init__(self):
        super().__init__()

        self.kernel = tf.Variable(
            tf.random.normal([3, 3, 3, 4]),
            name="kernel"
        )

        self.bias = tf.Variable(
            tf.zeros([4]),
            name="bias"
        )

    @tf.function(
        input_signature=[
            tf.TensorSpec([None, 8, 8, 3], tf.float32, name="input")
        ]
    )
    def __call__(self, x):
        z = tf.nn.conv2d(
            input=x,
            filters=self.kernel,
            strides=[1, 1, 1, 1],
            padding="SAME"
        )
        z = tf.nn.bias_add(z, self.bias)
        y = tf.nn.relu(z)
        return y
```

模型中涉及的主要 Tensor：

| Tensor | Shape | 原始数据类型 | 作用 |
|---|---|---|---|
| Input | `[1, 8, 8, 3]` | FP32 | 输入数据 |
| Kernel | `[3, 3, 3, 4]` | FP32 | 卷积权重 |
| Bias | `[4]` | FP32 | 卷积偏置 |
| Conv Output | `[1, 8, 8, 4]` | FP32 | 卷积结果 |
| ReLU Output | `[1, 8, 8, 4]` | FP32 | 最终输出 |

这里的 Input、Conv Output 和 ReLU Output 是计算图中的 Tensor。模型文件通常保存它们的形状、类型等描述，不会把每次推理产生的输入和中间结果都作为常量数据保存。

### 4.2 Full Integer Quantization 后的数据类型

一个典型的 TFLite INT8 Conv2D 模型，其主要数据类型可能是：

| Tensor | 原始模型 | Full INT8 模型 |
|---|---|---|
| Input | FP32 | INT8 |
| Kernel | FP32 | INT8 |
| Bias | FP32 | INT32 |
| Conv Output | FP32 | INT8 |
| ReLU Output | FP32 | INT8 |

其中 Bias 特别值得注意：

**Bias 通常不是 INT8，而是 INT32。**

卷积计算需要对多个 INT8 乘积进行累加。累加结果可能远远超出 INT8 范围，因此通常使用 INT32 累加器，Bias 也使用与累加结果匹配的 INT32 表示。

对于常见 TFLite INT8 Conv2D 量化约定：

- Input 使用自己的 Scale 和 Zero Point。
- Weight 使用 INT8，权重 Zero Point 为 0。
- Weight 可以按输出通道使用不同 Scale。
- Bias 使用 INT32。
- 每个输出通道的 Bias Scale 为 Input Scale 与该通道 Weight Scale 的乘积。
- 输出 Tensor 有自己的 Scale 和 Zero Point。

具体要求应以所采用的 TFLite 算子量化规范为准。

### 4.3 量化后的 Kernel 保存内容

假设 Kernel 的 Shape 为 `[3, 3, 3, 4]`：

```text
kernel:
    dtype = int8
    shape = [3, 3, 3, 4]

    data = [
        13, -24, 57, -89, ...
    ]

    quantization:
        scale = [
            0.010,
            0.015,
            0.008,
            0.020
        ]

        zero_point = [
            0, 0, 0, 0
        ]

        quantized_dimension = 3
```

这里仅为说明结构的示意数值，并非某次真实 Converter 输出。

需要保存的信息包括：

- INT8 权重数据。
- Scale。
- Zero Point。
- Per-Channel 量化时对应的量化维度。

### 4.4 Bias 的量化参数

Bias 的数据类型通常为 INT32：

```text
bias:
    dtype = int32
    shape = [4]

    data = [
        1200,
        1667,
        -2250,
        1650
    ]

    quantization:
        scale = [
            input_scale * weight_scale[0],
            input_scale * weight_scale[1],
            input_scale * weight_scale[2],
            input_scale * weight_scale[3]
        ]

        zero_point = [0, 0, 0, 0]
```

Bias 的量化关系：

\[
S_{bias,c}=S_{input}\times S_{weight,c}
\]

其中 \(c\) 表示输出通道。

因此，Bias 需要与输入和对应输出通道的权重量化参数保持一致。

### 4.5 参数存储空间对比

Kernel：

\[
3\times3\times3\times4=108
\]

Bias：

\[
4
\]

| 参数 | FP32 | INT8 模型 |
|---|---:|---:|
| Kernel | 108 × 4 = 432 Bytes | 108 × 1 = 108 Bytes |
| Bias | 4 × 4 = 16 Bytes | 4 × 4 = 16 Bytes |
| 合计 | 448 Bytes | 124 Bytes |

这里只计算 Kernel 和 Bias 的原始数值数据，不包括 Scale、Zero Point、Tensor 描述、算子参数、对齐填充等元数据。

因此，不能认为所有 INT8 模型文件都恰好是 FP32 文件大小的四分之一。对于大型模型，权重数据通常占主要部分，量化收益会更加明显。

## 5. 量化对运行时内存的影响

量化不仅影响模型文件中的常量参数，还会影响推理时的 Tensor 数据大小。

例如：

Input：

\[
1\times8\times8\times3=192\text{ elements}
\]

Output：

\[
1\times8\times8\times4=256\text{ elements}
\]

| Tensor | FP32 运行时数据量 | INT8 运行时数据量 |
|---|---:|---:|
| Input | 192 × 4 = 768 Bytes | 192 × 1 = 192 Bytes |
| Output | 256 × 4 = 1024 Bytes | 256 × 1 = 256 Bytes |

对于相同 Shape 的 Tensor，INT8 数据量是 FP32 的四分之一。

需要区分模型文件和运行时内存：

- **Kernel、Bias 等常量数据**：可以保存在 `.tflite` 文件的 Buffer 中。
- **Input、Output、Intermediate Activation 的实际数据**：通常在推理运行时提供或分配。
- **模型中的 Tensor 描述**：保存 Shape、数据类型、量化参数等元信息，不等于保存了每次推理的实际 Tensor 内容。

这对 TFLM 的 Tensor Arena、NPU SRAM 规划、DMA 搬运和 Tiling 都有直接影响。

## 6. 量化后的 Conv2D 如何计算？

量化不仅是把 FP32 权重换成 INT8 权重，计算过程也需要适配整数表示。

### 6.1 FP32 卷积

\[
Y=X\times W+B
\]

其中 X、W、B 和 Y 通常都是 FP32。

### 6.2 INT8 卷积与 INT32 累加

对某个输出通道 \(c\)，典型的整数累加可以表示为：

\[
Acc_c=\sum_i(q_{x,i}-Z_x)(q_{w,i,c}-Z_{w,c})+q_{bias,c}
\]

对于常见 TFLite INT8 Conv2D 权重量化，\(Z_{w,c}=0\)，所以：

\[
Acc_c=\sum_i(q_{x,i}-Z_x)q_{w,i,c}+q_{bias,c}
\]

其中：

- 输入：INT8。
- 权重：INT8。
- Bias：INT32。
- 累加结果：INT32。

### 6.3 Requantization

INT32 累加结果不能直接当作最终 INT8 输出使用，需要转换到输出 Tensor 的量化尺度。

\[
q_y=round\left(
Acc_c\times\frac{S_xS_{w,c}}{S_y}
\right)+Z_y
\]

随后还需要按照目标数据类型范围进行饱和限制（clamping）。

实际高性能整数内核通常会把比例因子实现为定点乘数和移位，而不是直接执行浮点除法或乘法。具体舍入和溢出行为应符合算子实现规范。

为什么需要 Requantization？

- Input 有自己的 Scale。
- Weight 有自己的 Scale。
- Output 有自己的 Scale。
- 乘法和累加结果的尺度，与输出 Tensor 的尺度通常不同。

因此，需要把累加结果重新映射到输出 Tensor 的整数范围。

### 6.4 量化 ReLU

ReLU：

\[
ReLU(x)=\max(0,x)
\]

量化后的整数 0 不一定代表真实数值 0。若输出 Zero Point 为 \(Z_y\)，则真实数值 0 对应的量化整数就是 \(Z_y\)。

因此，量化 ReLU 可以理解为对输出整数进行下限限制：

\[
q_y \geq Z_y
\]

实际实现还要考虑算子融合、输出范围限制和具体量化规范。

## 7. 常见量化方案及其模型表示

并不是所有量化方式都会把整个模型转换成 INT8。

| 方案 | Weight | Bias | Activation | 说明 |
|---|---|---|---|---|
| FP32 原始模型 | FP32 | FP32 | FP32 | 原始浮点模型 |
| FP16 权重量化 | FP16 | 视转换方式而定 | 通常仍可为 FP32 | 主要降低权重存储量；不等于全 FP16 推理 |
| Dynamic Range Quantization | 通常 INT8 | 依算子实现而定 | 通常运行时仍以浮点表示为主，可在内核内部动态量化 | 主要量化权重 |
| Full Integer Quantization | INT8 | 通常 INT32 | INT8 | 适合整数 NPU 推理 |
| QAT INT8 | 最终可为 INT8 | 通常 INT32 | 最终可为 INT8 | 训练阶段模拟量化，最终格式取决于导出配置 |

注意：

1. Dynamic Range Quantization 并不意味着模型所有 Tensor 都是 INT8。
2. QAT 是训练方法，不是独立的最终存储格式。
3. FP16 权重量化也不意味着所有 Activation 和运算都使用 FP16。
4. 最终数据类型必须查看实际生成的 TFLite 模型，不能仅根据量化方案名称推断。

## 8. 量化后的模型保存在哪里？

假设原始模型保存为 TensorFlow SavedModel：

```text
conv_relu/
├── saved_model.pb
└── variables/
    ├── variables.index
    └── variables.data-00000-of-00001
```

原始模型中的 Kernel、Bias 通常以 FP32 变量形式保存。

执行 PTQ 后，通常生成一个新的模型文件：

```text
conv_relu/
├── saved_model.pb
└── variables/
    ├── variables.index
    └── variables.data-00000-of-00001

conv_relu_int8.tflite
```

**PTQ 通常不会原地修改 SavedModel，而是读取原始模型并生成新的量化部署模型。**

### 8.1 TFLite FlatBuffer 中的逻辑结构

量化后的 `.tflite` 文件可以从以下逻辑结构理解：

```text
TFLite Model
│
├── OperatorCodes
│
├── Subgraphs
│   │
│   ├── Tensors
│   │   ├── Input       INT8
│   │   ├── Kernel      INT8
│   │   ├── Bias        INT32
│   │   └── Output      INT8
│   │
│   └── Operators
│       └── CONV_2D
│
└── Buffers
    ├── Kernel INT8 data
    └── Bias INT32 data
```

这是逻辑结构示意，不是完整的 FlatBuffer 二进制布局。

Tensor 描述中需要关注：

```text
Tensor:
    name
    shape
    type

    quantization:
        scale
        zero_point
        quantized_dimension
```

其中：

| 字段 | 作用 |
|---|---|
| `name` | Tensor 名称 |
| `shape` | Tensor 形状 |
| `type` | 数据类型，例如 FLOAT32、INT8、INT32 |
| `scale` | 量化缩放参数 |
| `zero_point` | 量化零点 |
| `quantized_dimension` | Per-Channel 量化参数对应的维度 |
| `Buffer` | 常量 Tensor 的实际数据所在位置 |

### 8.2 量化与算子融合是两件不同的事情

例如原始图：

```text
Conv2D
   |
   v
BiasAdd
   |
   v
ReLU
```

量化会改变 Tensor 的数据类型和数值表示。

图优化则可能把这些操作融合为一个带有融合激活属性的 Conv2D：

```text
CONV_2D
    fused_activation = RELU
```

是否发生融合取决于图转换优化和目标格式的表示能力。

因此：

- **量化**：改变数值表示和数据类型。
- **算子融合**：改变计算图中的算子组织形式。
- 两者可以同时发生，但不是同一个过程。

## 9. 对 NPU 软件栈和硬件设计的影响

量化会影响 NPU 软件栈的多个环节。

| 软件栈模块 | 需要处理的量化内容 |
|---|---|
| 模型导入 | 识别 FP32、FP16、INT8、INT32 等数据类型 |
| 模型量化 | 确定 Scale、Zero Point 和量化粒度 |
| 图编译器 | 判断算子是否支持对应量化格式 |
| 算子库 | 实现 INT8 Conv2D、Pooling 等算子 |
| Tiling | 根据数据位宽和布局计算分块 |
| 内存规划 | 根据 Tensor 数据类型计算内存占用 |
| DMA 调度 | 根据数据位宽和搬运长度计算传输量 |
| 命令生成 | 将量化参数转换为硬件可识别的配置 |
| NPU Runtime | 管理量化输入、输出和执行过程 |
| NPU Driver | 配置硬件计算参数和寄存器 |

### 9.1 图编译器需要读取什么？

例如，图编译器读取一个 TFLite INT8 Conv2D：

```text
Input:
    type = INT8
    scale = 0.02
    zero_point = -10

Weight:
    type = INT8
    per-channel scale = [0.01, 0.02, 0.03, 0.04]
    zero_point = 0

Bias:
    type = INT32

Output:
    type = INT8
    scale = 0.05
    zero_point = -5
```

以上是说明用的示意值，不是某个真实模型的导出结果。

图编译器需要判断：

1. 是否支持 INT8 Conv2D。
2. 是否支持 Per-Channel Weight Scale。
3. 是否支持 INT32 Accumulator。
4. 是否支持对应的 Requantization。
5. 是否支持量化 ReLU。
6. 算子之间是否需要额外的量化转换。
7. 当前量化配置是否符合 NPU 的硬件限制。

如果硬件不支持某些量化形式，编译器可能需要插入转换操作、选择其他内核，或将相关算子回退到 CPU。

### 9.2 NPU 硬件需要考虑哪些能力？

| 硬件模块 | 需要支持的能力 |
|---|---|
| MAC Array | INT8 × INT8 |
| Accumulator | INT32 累加 |
| Bias Path | INT32 Bias 加法 |
| Requantization | 定点乘法、移位、舍入、饱和 |
| Activation | INT8 ReLU、Clamp |
| Quantization Parameters | Scale、Zero Point 或等价的定点参数 |
| Data Path | 支持不同位宽 Tensor 的读写和布局 |

这说明量化不仅是软件编译器的事情，也会直接影响 NPU 的微架构设计。

## 10. 核心概念总结

| 问题 | 结论 |
|---|---|
| 什么是量化？ | 将高精度数值映射为低位宽数值表示 |
| 为什么量化？ | 减少模型存储、数据搬运和计算成本，通常有助于降低功耗 |
| 量化发生在哪里？ | 通常在模型训练之后、部署模型生成过程中；QAT 则在训练阶段模拟量化 |
| 是否需要重新训练？ | PTQ 通常不需要；QAT 需要训练或微调 |
| Weight 会改变吗？ | 量化模型中通常从 FP32 变为 INT8 等低精度表示 |
| Bias 会改变吗？ | Full INT8 Conv2D 中通常变为 INT32 |
| Activation 会改变吗？ | Full Integer Quantization 中通常为 INT8 |
| 是否需要额外参数？ | 需要 Scale、Zero Point 等量化元数据 |
| 原始 SavedModel 会改变吗？ | PTQ 通常不修改原始 SavedModel，而是生成新的量化模型 |
| NPU 为什么需要理解量化？ | 计算、存储、数据搬运、输出重定标都受量化影响 |
